## Repository Status

**Schema is now `beacon_v2`.** The frontend (`frontend/src/data.js`: `db: { schema: "beacon_v2" }`) reads and writes exclusively from the consolidated `beacon_v2` schema. The legacy `beacon` schema is still present in the database as a backup / read-only reference, but **no application code points at it from the frontend**. Data was one-shot backfilled via `supabase/migrations_v2/20260428122000_data_backfill.sql` (preserves UUIDs across schemas — alert subject_row_id references, auth_user_id linkages, and source_*_id lineage all survived). See "Schema state — v1 → v2 transition" below for the gotchas this creates.

Frontend running with all major features implemented; UI responsive across phone / tablet / desktop. **Creates persist** to Supabase (New-X modals, auth seeder, **the full alerts pipeline — schedule, dispatch, log**). **Inline and drawer edits persist** across every visible table (Potential, Awaiting, Awarded, Closed Out, Events, Hot Leads, Clients, Companies, Anticipated Invoice, Sub Invoices) — each `update*` in App.jsx runs an optimistic local setState followed by a scoped `supabase.from(table).update(dbPatch).eq("id", id)`. Multi-PM edits, event attendees, and lead attendees diff the old vs new array and mirror into the corresponding join table (`project_pms`, `anticipated_invoice_pms`, `event_attendees`, `lead_attendees`). Move-forward transitions persist to v2 (status flips on `projects`, INSERT into `anticipated_invoice` for billing transitions).

Alerts are wired end-to-end in code (AlertModal → `beacon_v2.alerts`/`alert_recipients`/`alert_fires` → GitHub Actions cron → `send-alert` Edge Function → Resend). Actual email delivery needs a one-time deploy: `supabase functions deploy send-alert`, set function secrets (`RESEND_API_KEY`, `ALERT_FROM_EMAIL`, `APP_URL`, `ALERTS_ENABLED=true`), and set the GitHub repo secrets `SEND_ALERT_URL` + `SEND_ALERT_AUTH`. **`send-alert` was migrated to `beacon_v2` in the 2026-06 timekeeping rollout** — it now serves `project`/`invoice`/`event`/`lead`/`timesheet` subjects from the v2 schema. Redeploy required to pick up the change.

**Outlook calendar sync** is wired end-to-end (Microsoft Graph `/calendarView/delta` → `outlook-sync` Edge Function → events upsert with sticky `type`/`status`/`notes`).   - `20260605120000_timekeeping_out_intervals.sql` — **Punched-OUT periods become first-class intervals; punch DIRECTION (not category) drives counting + color.** Adds `time_intervals.is_out boolean` and rewrites the four trigger functions. Before this, only at-desk (IN) sessions were stored — a punch-out *closed* the open interval and opened nothing, so the away period (e.g. 10:00–12:00) had no row and the punch-out "tag your session" prompt fell back to overwriting the *preceding IN session*. Now every punch TOGGLES: `fn_punch_reconcile` closes the open interval AND opens a fresh one of the opposite presence (punch-out → an open OUT interval = "currently out"; punch-in → an open IN interval). Semantics: **IN (`is_out=false`) = at desk → counts as worked time, green; OUT (`is_out=true`) = physically out → never counts, red, regardless of category** (the category is now only a *label* of where the person is, shown on the personal + Team timelines). `fn_classify_interval` applies the time-of-day rules to OUT intervals only (IN is always `work`) — fixing a latent bug where at-desk sessions before 16:00 CT were mislabeled `meeting_untagged`. `fn_recompute_day` sums worked minutes from IN intervals only (OT = `minutes_work - 480`); OUT intervals feed the informational per-category buckets but never the total; `missing_out` fires only for an open *IN* interval crossing midnight. `fn_rebuild_user_day` rebuilds a contiguous alternating-presence interval chain (1st=IN, 2nd=OUT, …) preserving user/admin/outlook overrides by `(start_at, end_at)`. **Requires redeploy of `timeclock-punch` (state now = open IN, not just any open interval) and `timeclock-classify` (now scopes to `is_out=true`).** Frontend colors intervals via `intervalTone(iv)` in `data.js` (green=IN, rose=OUT) — never by `TK_CATEGORY_TONE` anymore — and counts worked time as `minutes_work` only across every Team/Week/Day total.
  - `20260606120000_correction_add_interval.sql` — **Adds the `add_interval` correction kind** (`ALTER TYPE beacon_v2.correction_kind_enum ADD VALUE IF NOT EXISTS 'add_interval'`). Backs the Worked/Away toggle on the "Add New Time" block in `CorrectionModal`: one atomic correction carrying `{start_at, end_at, is_out, category, note}` instead of the old two-separate-`add_punch` flow (which an admin could half-approve, flipping the rest of the day's presence). On approval `timeclock-admin` inserts BOTH boundary punches, calls `fn_rebuild_user_day` (presence falls out of punch order — two punches inside an IN block carve a middle OUT block, the lunch case), then stamps the carved interval's `category` with `category_source='user'` keyed on the exact `(start_at, end_at)` so the user's label survives every later rebuild. **Requires redeploy of `timeclock-admin`.** Note: a freshly-added enum value can't be USED in the same transaction it's added in — this migration only declares it, so re-paste is safe.
  - `20260606120100_rebuild_dedup_punches.sql` — **Hardens `fn_rebuild_user_day` against DUPLICATE-INSTANT punches.** The day is rebuilt by walking punches in time order and TOGGLING presence on each (1st interval IN, 2nd OUT, …), so presence is a pure function of cumulative punch parity. Two punches on the EXACT same timestamp (e.g. an `add_interval` boundary colliding with an `edit_punch` or separate `add_punch`) produced a ZERO-LENGTH interval that still consumed a parity slot — flipping the IN/OUT of every later interval (symptom: an "away" block renders green/IN and the next block renders red-untagged/OUT). ## Schema state — v1 → v2 transition

There are two schemas live in the same database:

| Schema | Status | Who reads/writes |
|---|---|---|
| `beacon_v2` | **Live; canonical for the app.** | The frontend (`data.js`) — every PostgREST call routes through `db: { schema: "beacon_v2" }`. |
| `beacon` | Legacy; left in place as a backup snapshot from the cutover. | All three long-running Edge Functions (`send-alert`, `admin-users`, `outlook-sync`) have been **migrated to `beacon_v2`** — each pending a redeploy for the change to take effect. The seed/ingest scripts under `scripts/` still target `beacon`. |

**Gotchas this creates:**

1. **`send-alert` is now on `beacon_v2`** (was the long-standing gotcha here). Requires redeploy (`supabase functions deploy send-alert --project-ref ggqlcsppojypgaiyhods`) for the new code to take effect. The `SUBJECT_TABLE` map collapsed from 8 v1 keys to 5 v2 keys: `project` (unified `projects` table, branches on `row.status` for per-stage subject phrasing), `invoice`, `event`, `lead`, and `timesheet` (new — for the timekeeping classifier's "tag your meeting" reminders).
2. **`outlook-sync` is now pointed at `beacon_v2`** (was `beacon`). Same fix story as `admin-users`: schema parity is exact (`events`, `event_attendees`, `outlook_sync_state` all carry the Outlook provenance columns and the delta-cursor singleton in v2), so the swap was config-only — no code changes. **Requires redeploy** (`supabase functions deploy outlook-sync --project-ref ggqlcsppojypgaiyhods`) for the change to take effect. After redeploy, the cron will start writing to `beacon_v2.events` and the v2 frontend's calendar will see synced rows. Note: any events the function previously upserted into legacy `beacon.events` stay there as historical snapshots — they aren't auto-mirrored, and the delta cursor is per-schema (each schema has its own `outlook_sync_state.delta_link`), so the first run against v2 is effectively a full ±12-month rebuild and will take longer than steady-state ticks.
3. **`admin-users` is now pointed at `beacon_v2`** (was `beacon`). This was the cause of "deletes don't actually delete" — the v1 row was removed and the auth user was removed, but `beacon_v2.users` (what the frontend reads) was never touched, so the user appeared to remain on refresh. **Requires redeploy** (`supabase functions deploy admin-users --project-ref ggqlcsppojypgaiyhods`) for the change to take effect. After redeploy, role / ban / create / delete all land on the same schema the frontend reads, so UI and DB stay in sync. Side effect: creating a user via the function now leaves only a stub row in legacy `beacon.users` (the v1 trigger fires on auth-user creation and inserts an email-only row) — harmless, since `beacon` is documented as a cold backup.
4. **Ingest scripts under `scripts/` write to `beacon`.** They have not been migrated to v2. If you re-run `ingest_seed_data.py` or `sync_2026_invoice.py` today, you'll be repopulating the legacy schema — the v2 frontend won't see the changes until a fresh `data_backfill.sql` re-mirrors. For ongoing operational refreshes (e.g. the 2026 invoice sync), prefer making the same edits directly through the frontend or via Studio SQL against `beacon_v2`.

When in doubt: the frontend is the source of truth for what data is *visible to users*; `beacon_v2` is the source of truth for what data the frontend can see; `beacon` is a cold backup.

## Core Domain Architecture

The entire product is a **staged pipeline** with data carry-forward between stages. **Two first-class entry points** — Proposals (submitted proposals; status key `awaiting`, renamed from "Awaiting Verdict" in the 2026-06 IA restructure) and Potential (direct opportunities / billing candidates). Everything downstream is reached by Move Forward.

In v2 the four pipeline stages live in **one table**, `beacon_v2.projects`, keyed on `status` ∈ (`potential` | `awaiting` | `awarded` | `closed_out`). Stage-specific columns are gated by CHECK constraints. SOQ has been removed entirely (no table, no tab, no Move Forward path). **Open Bids** sits *before* the `projects` table as a standalone stage (its own table — `beacon_v2.open_bids`) and feeds into Proposals via an admin approval gate.

**2026-06 IA restructure — the navbar shows GROUPED pages; tab keys are unchanged** (old `?tab=` deep links from alert emails still work): **Leads & Bids** (= Hot Leads · Open Bids sub-tabs) → **Proposals & Awarded** (= Proposals · Awarded sub-tabs; the Awarded single/multi-list/others view toggle was removed — one table) → **Potential** → **Invoice** (= Invoices · In-Between · Closed Out sub-tabs; the Closed Out navbar tab moved here). Sub-tabs are an underline strip (`.subtabs`) under the page head; `NAV_GROUPS`/`SUB_TABS`/`TAB_META` in App.jsx drive it, and the rail pill remembers the last sub-tab used per group.

Transition semantics in v2:
- **UPDATE** (status flip on the same row): `awaiting → awarded`, `awaiting → closed_out`. Matches the "a proposal has only one verdict" mental model. The row never moves between tables — only its `status` changes — so lineage is intrinsically preserved.
- **INSERT-with-lineage** (a new row is created, source row stays): `openbids → awaiting` (new `projects` row with `status='awaiting'`; the `open_bids` row records `moved_to_project_id` and stays as the historical breadcrumb), `awarded → potential` (new `projects` row with `status='potential'` and `source_project_id` pointing back at the awarded row), `awarded → invoice` and `potential → invoice` (new `anticipated_invoice` row with `source_project_id` pointing at the project). The unique partial index on `(source_project_id, year)` means at most one auto-created invoice per source-project per year. **Note: the Potential → Invoice path now also deletes the source Potential row** — the user-facing semantic became "convert this Potential into an Invoice" rather than "track them in parallel."
- **billing_state flip (invoice rows; 2026-06)**: `invoice ⇄ between` (pause/resume — instant row actions, no panel) and `invoice/between → closed` (the `invoice→closed` MoveForwardPanel: rows flip `billing_state='closed'` — **never deleted** — and the upstream project flips `status='closed_out'`, or a closed_out stub is minted when there's no source). Reopen paths (`closed → invoice`, and `awarded → invoice` on a project with archived rows) **revive** the existing rows instead of inserting — so attachments/months/notes return intact and the `(source_project_id, year)` unique index can't collide. `awarded → invoice` now also persists its INSERT (it was local-only before) and auto-links the awarded row to the invoice project number.
- The single `source_project_id` FK on both `projects` and `anticipated_invoice` replaces v1's split (`source_potential_id` + `source_awaiting_id` on `projects`, `source_potential_id` + `source_awarded_id` on `anticipated_invoice`).
- **Open Bids approval is admin-only and DB-enforced.** Non-admin updates to `open_bids.approval_status / approved_by / approved_at` raise `42501` (insufficient_privilege) at a BEFORE UPDATE trigger — defense-in-depth on top of the UI gate (App.jsx hides the thumbs-up / thumbs-down on the Open Bids table for non-admin users). Move-forward to Awaiting Verdict requires `approval_status='approved'`.

Non-obvious behaviors that must be preserved:

1. **Carry-forward on stage transition.** When a row moves to the next stage, shared columns are copied automatically; the user is prompted **only** for fields new to the destination stage. The source row stays linked to the destination row (history is traceable). See PLAN.md for the exact per-stage field lists — they are not symmetric.
2. **Edit propagation is an open question.** PLAN.md explicitly flags: when a shared field is edited in a destination row, should the source row update too? Ask the user before picking a default.
3. **Contract amount lives on the project row**, never on Client or Company master records. A client can appear on many projects at different amounts.

   **Prime is also a first-class project-row field, independent of role.** Awarded rows have a dedicated Prime column (the picker spans the merged client+company list); the value lands on either `prime_client_id` (clients) or `prime_company_id` (companies) — never both. Pickers that span the merged list use a router pattern so writes hit the right column: `routeClientPick(uuid)` for Client, `routePrimePick(uuid)` for Prime. These routers live in `data.js` and are called by the App.jsx updaters *after* `buildDbPatch` runs, since `clientId`/`primeId` are deliberately not in the `*_COLS` whitelists. The `adaptAwarded` reader prefers the stored `role` column and only falls back to the legacy `prime_company_id IS NULL` heuristic when a row predates the column.
4. **People fields are user tags, not free text, and are multi-valued.** PM, attendees, alert recipients all resolve to `users` rows. v2 collapsed v1's six byte-identical `*_pms` join tables (potential_project_pms, awaiting_verdict_pms, awarded_project_pms, closed_out_project_pms, soq_pms, anticipated_invoice_pms) into **two**: `project_pms (project_id, user_id)` covers every status of `projects`; `anticipated_invoice_pms (anticipated_invoice_id, user_id)` covers Invoice. Composite PKs as before. The UI still models this as `row.pmIds: string[]` end-to-end (table cells render a `<UserStack>`, drawer uses a multi-user picker, CreateModal uses `UserMultiPicker`, PDF export joins names with `, `).
5. **Anticipated Invoice is manually created from Awarded or Potential.** There is no auto-create on the `awaiting → awarded` move — the user clicks "Move → Invoice" from either the Awarded or Potential tab to spawn a linked Invoice row (INSERT into `anticipated_invoice` with `source_project_id`). On the Potential → Invoice path, the source Potential row is then deleted (the user model for that path became "convert", not "track in parallel"); on the Awarded → Invoice path, the Awarded row stays as a historical log. The only remaining automatic Invoice creation is the **Orange-bucket shortcut**: creating a Potential with `probability=Orange` still spawns an Invoice row at insert time, linked via `anticipated_invoice.source_project_id` (uniqueness via the partial index on `(source_project_id, year)`). Invoice rows from the manual path carry Project Number, Project Name, PMs, Contract Amount, and Invoice Type (ENG/PM). Move Forward transitions persist to Supabase end-to-end.
6. **Actual vs. Projection split is date-driven, not a flag.** In the Invoice table, months ≤ the cutover-adjusted boundary render as editable "Actual"; later months render as "Projection". **The cutover is configurable** (Admin → Targets → "Move to Actual on") on two axes: `app_settings.invoice_actual_cutover_day` (1–31, default 1) and `invoice_actual_cutover_next_month` (bool, default false). Same-month mode: the current month flips on day N of the same month (day 1 = legacy "flips on the 1st"). Next-month mode: a month flips on day N of the *following* month (e.g. day 1 ⇒ June becomes Actual on July 1 — hold each month as a Projection until it ends). Computed by `actualThruMonth(cutoverDay, nextMonth)` in data.js and surfaced app-wide as `actualThru`; the amber vertical boundary line marks the **Actual▸Projection split** (the right edge of the last actual month — `i === actualThru`, CSS class `.month-today`), not "today." **Bill-attach promotion (per project, per month):** beyond the date cutover, a projected month is promoted to **Actual for that project** the moment a bill is attached to its total/prime cell — derived live from `r.primeFiles[i]` (re-annotated by `refreshInvoiceArtifacts` after every upload, so the cell flips instantly). `monthCellState(row, i, cue)` in `InvoiceTable` returns `month-actual` / `month-actual month-promoted` (the total/prime row gets the subtle "billed ahead" underline `.month-promoted`; the project's MSMM + sub rows for that month just go amber) / `month-proj`. The column header + cross-project grand totals stay on the global cutover, and the **YTD Actual column (labeled "Total Billed" in the UI — the header text was renamed; the math is unchanged) / Rollforward totals stay date-driven** (promotion is visual/status only, not folded into the YTD math); the PDF export mirrors the promotion via `invoiceCellStyle` (App.jsx). Also compute YTD MSMM Total Actual and MSMM Rollforward. **Attachments are allowed on EVERY month** (projected or actual) per the client's current policy. The lock lives behind the `ATTACH_ONLY_ON_ACTUAL` flag in data.js (currently `false`). Flip it to `true` to restore the lock: the per-cell paperclip then locks on projected months with no files (faded, non-opening "locked" clip), and the `InvoiceFilesModal` swaps its upload UI for a locked notice (`canAttach` prop) so the prime invoice-number chip isn't a bypass; the lock is **year-aware** via `isActualInvoiceMonth(year, monthIdx)` (whole past years actual, future years projected, current year splits at the cutover). Both gate sites (the `tables.jsx` clips + the `App.jsx` `canAttach` prop) read that one flag, so toggling the policy is a single-constant change. Amounts are always editable regardless.
7. **Invoice per-row overrides + writeback + file uploads.** `ytd_actual_override` and `rollforward_override` on `anticipated_invoice` let a user freeze either derived number. NULL = auto-calc; NOT NULL = display verbatim. Clearing the cell writes NULL. **All inline Invoice edits persist to Supabase**: the 12 month columns (`jan_amount`–`dec_amount`) via `updateInvoiceCell`, and `project_name`, `project_number`, `contract_amount`, `type`, `msmm_remaining_to_bill_year_start`, `year` via a whitelist in `updateInvoice` (`INVOICE_COL_MAP` in App.jsx). Writes are optimistic (local state first, then PATCH; no rollback on failure — a toast surfaces the error). PMs flow through `anticipated_invoice_pms` separately. **Per-month PDFs:** prime-side billing PDFs upload to Supabase Storage bucket `invoices` and are tracked in `prime_invoice_files (invoice_id, month, file_path, …)`. Sub-side billing has its own table — `sub_invoices (project_id, company_id, year, month, amount, paid)` for the per-(project, sub-firm, month) amount + the paid flag, and `sub_invoice_files` for the PDFs. Cascade-delete on the metadata rows; the frontend deletes the Storage binary first. **Prime/total per-month paid flags:** the "Project total" row carries its own 12 `{mon}_paid` booleans directly on `anticipated_invoice` (no separate table — the row is already year-scoped), toggled via `updateInvoicePrimePaid` and read back as `primePaid: boolean[12]`. Same three-state cell coloring as subs (attachment → yellow, paid → green, amount-only → red). See migration `20260606120300_prime_invoice_paid.sql`. **Paid cells lock once ticked:** marking paid is open to everyone, but UN-ticking is Admin-only and requires a confirm dialog. For non-admins a paid tick renders with a lock glyph + `not-allowed` cursor and clicking it just surfaces a "locked — only an administrator can unmark" toast; for admins, un-ticking routes through `requestPaidUntick` (App.jsx) → the reusable `ConfirmDialog` (panels.jsx). ## Auth & Roles

- **Login is required.** `App.jsx` boots with `phase="booting"` → reads the Supabase session → `phase="anon"` renders `LoginPage` (calls `signIn` then `fetchCurrentBeaconUser`) → `phase="loading"` runs `loadBeacon()` → `phase="ready"`. `onAuthStateChange` kicks cross-tab sign-outs back to `"anon"`.
- **Two roles, app-enforced + RLS-gated.** `beacon_v2.users.role` ∈ {`Admin`,`User`}. `isAdmin()` in `data.js` keys off the row fetched on login. Writes to `beacon_v2.users` are RLS-gated to Admin via `beacon_v2.is_current_user_admin()` — defense-in-depth so a compromised authenticated user can't flip their own role via direct PostgREST. SELECT stays open to authenticated + anon so PM/attendee pickers work. Other `beacon_v2.*` tables remain permissive-for-authenticated (plus prototype anon CRUD on most) — tighten further as admin-only actions accrue.
- **Admin drawer** lives on the gear icon: tabs = Users / **Alerts** / Appearance. Non-admins see the TweaksPanel (Appearance only) from the same gear. The Alerts tab widens the drawer to ~880px via an `admin-drawer-wide` modifier.
- **Edge Function auth patterns:**
  - `admin-users` — session JWT with `role='Admin'`, validated by re-fetching the users table on each call. (Still pinned to v1 `beacon.users`; works because UUIDs are shared across schemas, but role flips don't propagate to v2 — see the gotcha section.)
  - `send-alert` — dual: service-role bearer (GitHub Actions) **or** an Admin session JWT (the "Run tick now" button). Anon callers get 401/403.
- **Seeding auth users.** `scripts/seed_auth_users.py` mirrors every `beacon.users` row into `auth.users` with password `{first_name}123$` and `app_metadata.role`. Idempotent (PUT on match, POST on miss). Reads from v1 `beacon.users`; the v2 backfill carried IDs forward, so this still produces correct `auth.users` rows for the v2 frontend.
- **Anon write policies are a prototype shortcut.** `20260421120000_allow_anon_write.sql` opens full CRUD to `anon` so creates work before auth was wired. Now that login is live, the `anon insert/update/delete` policies (and the `anon read` policy) should be dropped on any table that should be sign-in-gated — see the security note inside that migration.

## Alerts dispatch pipeline

```
AlertModal  →  confirmAlert (App.jsx)                 ─┐
  • 3 inserts into beacon_v2: alerts + alert_recipients │
    + pending alert_fires (status='pending')            │   (every 60s)
                                                        │        │
                                                        ▼        ▼
                                       beacon_v2.alert_fires  ◀──  GH Actions cron
                                                                │    (alert-tick.yml)
                                                                ▼
                                                 send-alert Edge Function
                                                 1. claim_pending_fires (SKIP LOCKED, marks 'processing')
                                                 2. load alert + recipients + subject row
                                                 3. render email per subject_table
                                                 4. Resend (Idempotency-Key = fire.id:email)
                                                 5. complete_fire ─┬─ status='sent' + spawn next fire (tz-aware)
                                                                   ├─ status='failed' + error_message (retry ≤3)
                                                                   └─ status='skipped' (subject deleted, disabled, etc.)
```

(As of 2026-06 `send-alert` reads `beacon_v2` directly — the arrows above are the live flow once the function is redeployed.)

- **Kill switch:** `ALERTS_ENABLED=false` as an Edge Function secret short-circuits the handler → `{ok:true, disabled:true}`. No redeploy needed.
- **Logs:** `beacon_v2.alert_fires` IS the log table. Studio-friendly query:
  ```sql
  select f.status, f.scheduled_at, f.fired_at, f.error_message,
         a.subject_table, a.subject_row_id, a.recurrence
    from beacon_v2.alert_fires f
    join beacon_v2.alerts a on a.id = f.alert_id
   order by f.scheduled_at desc limit 50;
  ```
  The Dispatch Desk tab renders the same info with vitals + per-alert expand-for-history + retry buttons.
- **Deep links:** `send-alert` builds `{APP_URL}?tab=X&rowId=Y`. `App.jsx` reads query params on BeaconApp mount, sets tab, then a `pendingFocusRowId` effect auto-opens the DetailDrawer when rows include that id; URL cleared via `history.replaceState`.
- **Polymorphic subject resolution:** `alerts.subject_row_id` has no FK (it spans 4 tables in v2: `projects`, `anticipated_invoice`, `events`, `leads`). The Edge Function maps `subject_table` → DB table name and selects by id. A missing row → `skipped` + `is_active=false` on the alert (the BEFORE DELETE trigger also deactivates immediately).
- **Custom RRULE:** `recurrence_rule` is an iCal RRULE string. `complete_fire` returns without spawning for `recurrence='custom'`; the Edge Function parses the rule via `rrule` (npm) and inserts the next pending fire itself.

## Responsive design

The app runs at phone, tablet, and desktop widths. Entry point: `frontend/index.html`'s viewport is `width=device-width, initial-scale=1, viewport-fit=cover` (formerly pinned to `width=1440`, which forced mobile Safari to render the desktop layout zoomed-out). The responsive layer lives entirely in `frontend/src/styles.css` — no per-component breakpoint JS except the tab-rail auto-scroll.

- **Breakpoint ladder** (mobile-first overrides appended to the end of `styles.css`, ~280 lines): ≤1280 → ≤1024 → ≤840 → ≤640 → ≤440. Plus `@media (hover: none) and (pointer: coarse)` for touch-target sizing, landscape-phone re-centering of modals, `@media print`, and `@media (prefers-reduced-motion: reduce)`. 11 media-query blocks total.
- **Tables keep their grid columns and scroll horizontally** inside `.table-scroll` — we explicitly did NOT collapse to card views (user muscle memory for the grid is load-bearing). Each `.table-scroll` wraps header + rows in a `.table-scroll-body { min-width: min-content }` div so all rows render at a shared width. `min-content` (not `max-content`) is intentional: it resolves to the sum of track minimums (fixed px + `minmax()` first arg), which is exactly what the grid needs to render without clipping — `max-content` would additionally pull in cell-text intrinsic widths and inflate the wrapper past what the grid requires, causing spurious horizontal scroll on wide desktops.
- **Drawer → full-width on phone**; modals (`AlertModal`, `CreateModal`, `MoveForwardPanel`) convert to **bottom-sheets** on portrait phones (slide up from bottom, rounded top corners only) and **re-center** on landscape-phone geometries via `@media (max-height: 500px) and (max-width: 900px)` where a bottom-sheet would cover the whole viewport.
- **Pipeline tab rail horizontal-scrolls** below 1024 instead of wrapping to multiple rows. `App.jsx` holds a `pipelineRef` and runs a `useEffect` on `tab` that calls `scrollIntoView({ block: "nearest", inline: "center", behavior: "smooth" })` on the active tab — so programmatic tab changes, URL-param deep links, and stale touch-scrolled positions all recover the active tab.
- **Topbar collapses** on phones: `.brand-sub`, the decorative notifications bell, the (currently non-functional) search pill, and the session role chip all hide progressively. The session name hides before the avatar.
- **Stat strip** 4 → 3 → 2 columns; sparkline drops on phones so seven-figure values don't collide with the sparkline SVG.
- **iOS notch respected** via `env(safe-area-inset-*)` on topbar / tabs / page / toast.
- **Admin drawer + Dispatch vitals** reflow: vitals grid 5 → 3 → 2 cols, admin row drops badges onto a second grid row at ≤640 so name/email don't clip at 360 px.

## Progressive Web App (PWA)

The frontend ships as an installable PWA via `vite-plugin-pwa`. Configured in `frontend/vite.config.js`; runtime UI in `frontend/src/pwa.js` (subscribable store + SW registration) and `frontend/src/pwa-ui.jsx` (`PwaInstallChip`, `PwaOfflineChip`, `PwaUpdateToast`). App.jsx mounts the install chip + offline chip in the topbar and the update toast at the page root.

- **Update flow is opt-in, not silent.** `registerType: "prompt"` + `skipWaiting: false` means a new service worker waits in the background and the UI surfaces an "Update available" toast; the user clicks to activate (calls `_updateSW(true)` which reloads). This avoids surprising users mid-edit with a refresh.
- **Manual SW registration** — `injectRegister: false` in vite.config.js; we call `registerSW({ onNeedRefresh, onOfflineReady })` ourselves in `pwa.js` so the same store can also track `beforeinstallprompt` (install chip), `appinstalled` (auto-hide), and `online`/`offline` events (offline pill).
- **Supabase requests are NETWORK-ONLY.** Workbox `runtimeCaching` entries explicitly mark every HTTP verb against `VITE_SUPABASE_URL` as `NetworkOnly` — we never serve cached data from the database; if offline, the request fails and the offline chip surfaces. Google Fonts CSS is `StaleWhileRevalidate`, font files are `CacheFirst` for a year (URLs are content-hashed). `navigateFallbackDenylist` excludes `/api/`, `/functions/`, `/auth/`, `/realtime/` so the SW never returns `index.html` for those.
- **Cache budget:** `globPatterns` covers `js/css/html/ico/png/svg/webmanifest/woff/woff2`; `maximumFileSizeToCacheInBytes: 5 MB` ceiling per asset; `cleanupOutdatedCaches: true`.
- **`devOptions.enabled: false`** — the SW is **not active in `npm run dev`** (would just slow it down and cache stale dev bundles). To test SW behavior locally, flip to `true` or use `npm run build && npm run preview`.
- **Icons** are checked in under `frontend/public/` and regenerated from the source SVG via `npm run pwa:icons` (`frontend/scripts/generate-pwa-icons.mjs` using `@resvg/resvg-js`). Re-run when the brand mark changes.
- **Vercel cache-control headers** in `frontend/vercel.json` send `Cache-Control: public, max-age=0, must-revalidate` for `/sw.js` and `/workbox-*.js` (so update prompts actually arrive), plus `Service-Worker-Allowed: /` on `/sw.js`. Don't strip those when editing vercel.json.

## Seed Data Notes

The CSVs in `Data/` are exports from live spreadsheets and have the quirks you'd expect:
- Multi-row headers, merged cells, and category rows interleaved with data (e.g., `Org Type : Federal` as a section header in `Awarded Data/`).
- "Subs" appear as repeated columns with embedded dollar amounts in strings (`"$90,000 (survey)"`) — parse, don't assume clean numerics.
- Dates are inconsistent (`4/1/26`, `decision on 4/2/26`, blank). Normalize on ingest.
- Probability is encoded by color/legend in the source; the ingester maps section-total rows (`Total Amount (High Probability)` etc.) to probability values.
- The 2025 Potential file has no Prime/Sub or Client columns — per user direction, all 2025 rows ingest as `role='Prime'`, `client_id=NULL`.
- Three rows in 2026 Potential had the Client column holding the **prime** firm rather than the end-client (because MSMM was a Sub on them); hand-verified corrections are baked into `scripts/ingest_seed_data.py`.

## Hosting topology

Five hosts, distinct responsibilities:

| Host | What runs there | Config |
|---|---|---|
| **Vercel** | `frontend/` static Vite build + service-worker (PWA) | `frontend/vercel.json` (SPA rewrites, security headers, no-cache headers for `/sw.js` + `/workbox-*.js`, `Service-Worker-Allowed: /`), Project Settings → Root Directory = `frontend`, env vars `VITE_SUPABASE_URL` + `VITE_SUPABASE_ANON_KEY` |
| **Supabase** | Postgres + PostgREST + Edge Functions (`admin-users`, `send-alert`, `outlook-sync`, `timeclock-punch`, `timeclock-classify`, `timeclock-admin`, `generate-description`, `license-reminders`) + Storage buckets `invoices`, `bid-rfqs`, `license-files` (all private) | `supabase/migrations_v2/` applied via Studio SQL Editor (the live schema; `supabase/migrations/` is the legacy v1 backup); `supabase secrets set ...` for function env (`RESEND_API_KEY`, `ALERT_FROM_EMAIL`, `APP_URL`, `ALERTS_ENABLED`, `MS_GRAPH_TENANT_ID`, `MS_GRAPH_CLIENT_ID`, `MS_GRAPH_CLIENT_SECRET`, `OUTLOOK_MAILBOX`, `OUTLOOK_SYNC_ENABLED`, `TIMECLOCK_DEVICE_KEY`); `beacon_v2` and `beacon` both exposed in Settings → API |
| **GitHub Actions** | 1-min `alert-tick`, 15-min `outlook-sync-tick`, 5-min `timekeeping-classify-tick`, daily `license-reminders-tick` crons | `.github/workflows/alert-tick.yml`, `.github/workflows/outlook-sync-tick.yml`, `.github/workflows/timekeeping-classify-tick.yml`, `.github/workflows/license-reminders-tick.yml`; repo secrets `SEND_ALERT_URL`/`AUTH`, `OUTLOOK_SYNC_URL`/`AUTH`, `TIMECLOCK_CLASSIFY_URL`/`AUTH`, `LICENSE_REMINDERS_URL`/`AUTH` |
| **Raspberry Pi (office)** | NFC tap reader — reads fobs and POSTs to `timeclock-punch` (+ the `action:'tag'` follow-up). Either the 7" touchscreen kiosk (`pi/kiosk.py`, PyQt5) or the headless OLED daemon (`pi/timeclock.py`). | `pi/{kiosk,timeclock}.py` + `pi/systemd/{beacon-kiosk,timeclock}.service`, config in `/etc/beacon-timeclock/config.ini` on each Pi (bearer = same value as Supabase secret `TIMECLOCK_DEVICE_KEY`); kiosk needs Raspberry Pi OS Desktop + autologin |
| **Microsoft 365 / Azure AD** | Tenant-level App registration with `Calendars.Read` Application permission, scoped to `beacon@msmmeng.com` via Exchange Online RBAC for Applications (custom Management Scope + Role Assignment — provisioned by `scripts/setup_outlook_rbac.ps1`) | One-time setup; tenant ID + client ID + client secret captured into the Supabase function secrets above. Verify with `Test-ServicePrincipalAuthorization -Identity <AppId> -Resource beacon@msmmeng.com` (expect `Application Calendars.Read` in `GrantedPermissions`) and against any other mailbox (expect empty). |

After the first Vercel deploy, update Supabase's `APP_URL` secret to the deployed URL so alert-email deep links point to the right place. Preview deploys share production's Supabase — creating data on a preview writes to the real DB. Custom domain: add in Vercel → Domains, re-run `supabase secrets set APP_URL=...` to match.

## Working Style

- PLAN.md has several explicit "flag a preference here during build" points. Surface those to the user instead of silently choosing.
- Customer data under `Data/` is private — never commit it back (`.gitignore` excludes the directory). Supabase now holds the canonical copy.
- `frontend/.env.local` contains the anon public key (browser-safe, but still gitignored by convention).
