## Repository Status

**Schema is now `beacon_v2`.** The frontend (`frontend/src/data.js`: `db: { schema: "beacon_v2" }`) reads and writes exclusively from the consolidated `beacon_v2` schema. The legacy `beacon` schema is still present in the database as a backup / read-only reference, but **no application code points at it from the frontend**. Data was one-shot backfilled via `supabase/migrations_v2/20260428122000_data_backfill.sql` (preserves UUIDs across schemas — alert subject_row_id references, auth_user_id linkages, and source_*_id lineage all survived). See "Schema state — v1 → v2 transition" below for the gotchas this creates.

Frontend running with all major features implemented; UI responsive across phone / tablet / desktop. **Creates persist** to Supabase (New-X modals, auth seeder, **the full alerts pipeline — schedule, dispatch, log**). **Inline and drawer edits persist** across every visible table (Potential, Awaiting, Awarded, Closed Out, Events, Hot Leads, Clients, Companies, Anticipated Invoice, Sub Invoices) — each `update*` in App.jsx runs an optimistic local setState followed by a scoped `supabase.from(table).update(dbPatch).eq("id", id)`. Multi-PM edits, event attendees, and lead attendees diff the old vs new array and mirror into the corresponding join table (`project_pms`, `anticipated_invoice_pms`, `event_attendees`, `lead_attendees`). Move-forward transitions persist to v2 (status flips on `projects`, INSERT into `anticipated_invoice` for billing transitions).

Alerts are wired end-to-end in code (AlertModal → `beacon_v2.alerts`/`alert_recipients`/`alert_fires` → GitHub Actions cron → `send-alert` Edge Function → Resend). **Outlook calendar sync** is wired end-to-end (Microsoft Graph `/calendarView/delta` → `outlook-sync` Edge Function → events upsert with sticky `type`/`status`/`notes`).   - `20260605120000_timekeeping_out_intervals.sql` — **Punched-OUT periods become first-class intervals; punch DIRECTION (not category) drives counting + color.** Adds `time_intervals.is_out boolean` and rewrites the four trigger functions. Before this, only at-desk (IN) sessions were stored — a punch-out *closed* the open interval and opened nothing, so the away period (e.g. 10:00–12:00) had no row and the punch-out "tag your session" prompt fell back to overwriting the *preceding IN session*. ## Schema state — v1 → v2 transition

There are two schemas live in the same database:

| Schema | Status | Who reads/writes |
|---|---|---|
| `beacon_v2` | **Live; canonical for the app.** | The frontend (`data.js`) — every PostgREST call routes through `db: { schema: "beacon_v2" }`. |
| `beacon` | Legacy; left in place as a backup snapshot from the cutover. | All three long-running Edge Functions (`send-alert`, `admin-users`, `outlook-sync`) have been **migrated to `beacon_v2`** — each pending a redeploy for the change to take effect. The seed/ingest scripts under `scripts/` still target `beacon`. |

**Gotchas this creates:**

1. **`send-alert` is now on `beacon_v2`** (was the long-standing gotcha here). Requires redeploy (`supabase functions deploy send-alert --project-ref ggqlcsppojypgaiyhods`) for the new code to take effect. The `SUBJECT_TABLE` map collapsed from 8 v1 keys to 5 v2 keys: `project` (unified `projects` table, branches on `row.status` for per-stage subject phrasing), `invoice`, `event`, `lead`, and `timesheet` (new — for the timekeeping classifier's "tag your meeting" reminders).
2. **`outlook-sync` is now pointed at `beacon_v2`** (was `beacon`). Same fix story as `admin-users`: schema parity is exact (`events`, `event_attendees`, `outlook_sync_state` all carry the Outlook provenance columns and the delta-cursor singleton in v2), so the swap was config-only — no code changes. **Requires redeploy** (`supabase functions deploy outlook-sync --project-ref ggqlcsppojypgaiyhods`) for the change to take effect. After redeploy, the cron will start writing to `beacon_v2.events` and the v2 frontend's calendar will see synced rows. Note: any events the function previously upserted into legacy `beacon.events` stay there as historical snapshots — they aren't auto-mirrored, and the delta cursor is per-schema (each schema has its own `outlook_sync_state.delta_link`), so the first run against v2 is effectively a full ±12-month rebuild and will take longer than steady-state ticks.
3. **`admin-users` is now pointed at `beacon_v2`** (was `beacon`). This was the cause of "deletes don't actually delete" — the v1 row was removed and the auth user was removed, but `beacon_v2.users` (what the frontend reads) was never touched, so the user appeared to remain on refresh. **Requires redeploy** (`supabase functions deploy admin-users --project-ref ggqlcsppojypgaiyhods`) for the change to take effect. After redeploy, role / ban / create / delete all land on the same schema the frontend reads, so UI and DB stay in sync. Side effect: creating a user via the function now leaves only a stub row in legacy `beacon.users` (the v1 trigger fires on auth-user creation and inserts an email-only row) — harmless, since `beacon` is documented as a cold backup.
4. **Ingest scripts under `scripts/` write to `beacon`.** They have not been migrated to v2. If you re-run `ingest_seed_data.py` or `sync_2026_invoice.py` today, you'll be repopulating the legacy schema — the v2 frontend won't see the changes until a fresh `data_backfill.sql` re-mirrors. For ongoing operational refreshes (e.g. the 2026 invoice sync), prefer making the same edits directly through the frontend or via Studio SQL against `beacon_v2`.

When in doubt: the frontend is the source of truth for what data is *visible to users*; `beacon_v2` is the source of truth for what data the frontend can see; `beacon` is a cold backup.

## Applying migrations

The Supabase CLI is installed and logged in, but `supabase link` needs the project's DB password (separate from the service key in `.env`). Two paths:
1. `supabase link --project-ref ggqlcsppojypgaiyhods` then `supabase db push` (interactive password prompt).
2. Paste each migration into Supabase Studio → SQL Editor → Run.

After applying v2: **add `beacon_v2` to Dashboard → Settings → API → Exposed schemas.** PostgREST won't serve the schema otherwise. (`beacon` should already be exposed from the v1 era; leave it exposed until the Edge Functions are migrated off it.)

## Core Domain Architecture

The entire product is a **staged pipeline** with data carry-forward between stages. **Two first-class entry points** — Proposals (submitted proposals; status key `awaiting`, renamed from "Awaiting Verdict" in the 2026-06 IA restructure) and Potential (direct opportunities / billing candidates). Everything downstream is reached by Move Forward.

In v2 the four pipeline stages live in **one table**, `beacon_v2.projects`, keyed on `status` ∈ (`potential` | `awaiting` | `awarded` | `closed_out`). Stage-specific columns are gated by CHECK constraints. SOQ has been removed entirely (no table, no tab, no Move Forward path). **Open Bids** sits *before* the `projects` table as a standalone stage (its own table — `beacon_v2.open_bids`) and feeds into Proposals via an admin approval gate.

**2026-06 IA restructure — the navbar shows GROUPED pages; tab keys are unchanged** (old `?tab=` deep links from alert emails still work): **Leads & Bids** (= Hot Leads · Open Bids sub-tabs) → **Proposals & Awarded** (= Proposals · Awarded sub-tabs; the Awarded single/multi-list/others view toggle was removed — one table) → **Invoice** (= Invoices · In-Between · Closed Out sub-tabs; the Closed Out navbar tab moved here). Sub-tabs are an underline strip (`.subtabs`) under the page head; `NAV_GROUPS`/`SUB_TABS`/`TAB_META` in App.jsx drive it, and the rail pill remembers the last sub-tab used per group. **The Potential page was removed from the navbar** (2026-06 follow-up): the `potential` tab key + page render remain (deep links and Directory project-jumps still work) but it's unreachable from the rail; the Awarded "Move → Potential" row action is gone, the "Pipeline MSMM" stat was replaced by an "In-Between" (paused contract value) stat, and demoting an Orange invoice no longer navigates anywhere (toast instead). The rail itself was **redesigned from folder-tabs to a modern pill bar** (`.tab` is now a rounded pill — active = surface pill with a soft accent ring; thin `chevronRight` separators between pipeline groups; a `.tab-rail-divider` hairline before the side pages; the `.dot` markers are gone). **Every stage has an explicit move-forward affordance**: Hot Leads → Proposals (NEW — row/drawer forward button, MOVE semantics: a `projects status='awaiting'` row is inserted and the lead row is deleted; Undo re-inserts the lead + attendees), Open Bids → Proposals (approval-gated), Proposals → Awarded / Closed Out, Awarded → Invoice, Invoice ⇄ In-Between → Closed Out.

Transition semantics in v2:
- **UPDATE** (status flip on the same row): `awaiting → awarded`, `awaiting → closed_out`. Matches the "a proposal has only one verdict" mental model. The row never moves between tables — only its `status` changes — so lineage is intrinsically preserved.
- **INSERT-with-lineage** (a new row is created, source row stays): `openbids → awaiting` (new `projects` row with `status='awaiting'`; the `open_bids` row records `moved_to_project_id` and stays as the historical breadcrumb), `awarded → potential` (new `projects` row with `status='potential'` and `source_project_id` pointing back at the awarded row), `awarded → invoice` and `potential → invoice` (new `anticipated_invoice` row with `source_project_id` pointing at the project). The unique partial index on `(source_project_id, year)` means at most one auto-created invoice per source-project per year. **Note: the Potential → Invoice path now also deletes the source Potential row** — the user-facing semantic became "convert this Potential into an Invoice" rather than "track them in parallel."
- **billing_state flip (invoice rows; 2026-06)**: `invoice ⇄ between` (pause/resume — instant row actions, no panel) and `invoice/between → closed` (the `invoice→closed` MoveForwardPanel: rows flip `billing_state='closed'` — **never deleted** — and the upstream project flips `status='closed_out'`, or a closed_out stub is minted when there's no source). Reopen paths (`closed → invoice`, and `awarded → invoice` on a project with archived rows) **revive** the existing rows instead of inserting — so attachments/months/notes return intact and the `(source_project_id, year)` unique index can't collide. `awarded → invoice` now also persists its INSERT (it was local-only before) and auto-links the awarded row to the invoice project number.
- **MOVE-with-delete (hotleads → awaiting; 2026-06 follow-up)**: a Proposals project is inserted (title seeds the name, notes carry over, the lead's client routes via `routeClientPick` to `client_id`/`prime_company_id`, and the lead's **Anticipated Amount** pre-fills the proposal's **Client Contract** as formatted money — see `20260624120000`) and the `leads` row is **deleted** (the BEFORE DELETE trigger deactivates its alerts). Undo re-inserts the lead with its original id + `lead_attendees`. Config `"hotleads→awaiting"` in MoveForwardPanel; branch in confirmMove; forward buttons on the Hot Leads rows + drawer.
- **2026-07 persistence + reveal fixes on these paths:** `awaiting → awarded` / `awaiting → closed_out` now genuinely persist the in-place status flip (they previously mutated local state only and minted a client-side non-UUID id, so a later `awarded → invoice` insert failed with `22P02` invisibly — the UI had already jumped to the Invoice tab). The `awarded/potential → invoice` creates are **two-phase**: Phase 1 inserts the `anticipated_invoice` row (safe to roll back); Phase 2 (PM tag, MHZ sibling, awarded link) never discards the already-committed row on failure — a Phase-2 error used to revert local state, and the retry then tripped the `(source_project_id, year, type)` unique index ("already exists" with nothing visible anywhere). Every jump to the Invoice page routes through `revealInvoiceRow()` (App.jsx): it widens the shared Type filter to the target row's type and lands on the correct sub-tab (the filter defaults to ENG-only and is shared across Invoices / In-Between / Closed Out, so a PM / MHZ / paused / closed target would otherwise land on a view that hides it); `invTypeOk` (App.jsx) + `matchesType` (tables.jsx) normalize NULL type → "ENG" so legacy typeless rows aren't hidden under active filters.
- The single `source_project_id` FK on both `projects` and `anticipated_invoice` replaces v1's split (`source_potential_id` + `source_awaiting_id` on `projects`, `source_potential_id` + `source_awarded_id` on `anticipated_invoice`).
- **Open Bids approval is admin-only and DB-enforced.** Non-admin updates to `open_bids.approval_status / approved_by / approved_at` raise `42501` (insufficient_privilege) at a BEFORE UPDATE trigger — defense-in-depth on top of the UI gate (App.jsx hides the thumbs-up / thumbs-down on the Open Bids table for non-admin users). Move-forward to Awaiting Verdict requires `approval_status='approved'`.

Non-obvious behaviors that must be preserved:

1. **Carry-forward on stage transition.** When a row moves to the next stage, shared columns are copied automatically; the user is prompted **only** for fields new to the destination stage. The source row stays linked to the destination row (history is traceable). See PLAN.md for the exact per-stage field lists — they are not symmetric.
2. **Edit propagation is an open question.** PLAN.md explicitly flags: when a shared field is edited in a destination row, should the source row update too? Ask the user before picking a default.
3. **Contract amount lives on the project row**, never on Client or Company master records. A client can appear on many projects at different amounts.

   **Prime is also a first-class project-row field, independent of role.** Awarded rows have a dedicated Prime column (the picker spans the merged client+company list); the value lands on either `prime_client_id` (clients) or `prime_company_id` (companies) — never both. Pickers that span the merged list use a router pattern so writes hit the right column: `routeClientPick(uuid)` for Client, `routePrimePick(uuid)` for Prime. These routers live in `data.js` and are called by the App.jsx updaters *after* `buildDbPatch` runs, since `clientId`/`primeId` are deliberately not in the `*_COLS` whitelists. The `adaptAwarded` reader prefers the stored `role` column and only falls back to the legacy `prime_company_id IS NULL` heuristic when a row predates the column.
4. **People fields are user tags, not free text, and are multi-valued.** PM, attendees, alert recipients all resolve to `users` rows. v2 collapsed v1's six byte-identical `*_pms` join tables (potential_project_pms, awaiting_verdict_pms, awarded_project_pms, closed_out_project_pms, soq_pms, anticipated_invoice_pms) into **two**: `project_pms (project_id, user_id)` covers every status of `projects`; `anticipated_invoice_pms (anticipated_invoice_id, user_id)` covers Invoice. Composite PKs as before. The UI still models this as `row.pmIds: string[]` end-to-end (table cells render a `<UserStack>`, drawer uses a multi-user picker, CreateModal uses `UserMultiPicker`, PDF export joins names with `, `).
5. **Anticipated Invoice is manually created from Awarded or Potential.** There is no auto-create on the `awaiting → awarded` move — the user clicks "Move → Invoice" from either the Awarded or Potential tab to spawn a linked Invoice row (INSERT into `anticipated_invoice` with `source_project_id`). On the Potential → Invoice path, the source Potential row is then deleted (the user model for that path became "convert", not "track in parallel"); on the Awarded → Invoice path, the Awarded row stays as a historical log. The only remaining automatic Invoice creation is the **Orange-bucket shortcut**: creating a Potential with `probability=Orange` still spawns an Invoice row at insert time, linked via `anticipated_invoice.source_project_id` (uniqueness via the partial index on `(source_project_id, year)`). Invoice rows from the manual path carry Project Number, Project Name, PMs, Contract Amount, and Invoice Type (**ENG / PM / MHZ** — MHZ is a linked perspective of ENG, see the InvoiceTable note below + `20260706120100_mhz_invoice_perspectives.sql`). Move Forward transitions persist to Supabase end-to-end.
6. **Actual vs. Projection split is date-driven, not a flag.** In the Invoice table, months ≤ the cutover-adjusted boundary render as editable "Actual"; later months render as "Projection". **The cutover is configurable** (Admin → Targets → "Move to Actual on") on two axes: `app_settings.invoice_actual_cutover_day` (1–31, default 1) and `invoice_actual_cutover_next_month` (bool, default false). Same-month mode: the current month flips on day N of the same month (day 1 = legacy "flips on the 1st"). Next-month mode: a month flips on day N of the *following* month (e.g. day 1 ⇒ June becomes Actual on July 1 — hold each month as a Projection until it ends). Computed by `actualThruMonth(cutoverDay, nextMonth)` in data.js and surfaced app-wide as `actualThru`; the amber vertical boundary line marks the **Actual▸Projection split** (the right edge of the last actual month — `i === actualThru`, CSS class `.month-today`), not "today." **Bill-attach promotion (per project, per month):** beyond the date cutover, a projected month is promoted to **Actual for that project** the moment a bill is attached to its total/prime cell — derived live from `r.primeFiles[i]` (re-annotated by `refreshInvoiceArtifacts` after every upload, so the cell flips instantly). `monthCellState(row, i, cue)` in `InvoiceTable` returns `month-actual` / `month-actual month-promoted` (the total/prime row gets the subtle "billed ahead" underline `.month-promoted`; the project's MSMM + sub rows for that month just go amber) / `month-proj`. The column header + cross-project grand totals stay on the global cutover, and the **YTD Actual column (labeled "Total Billed" in the UI — the header text was renamed; the math is unchanged) / Rollforward totals stay date-driven** (promotion is visual/status only, not folded into the YTD math); the PDF export mirrors the promotion via `invoiceCellStyle` (App.jsx). Also compute YTD MSMM Total Actual and MSMM Rollforward. **Attachments are allowed on EVERY month** (projected or actual) per the client's current policy. The lock lives behind the `ATTACH_ONLY_ON_ACTUAL` flag in data.js (currently `false`). Flip it to `true` to restore the lock: the per-cell paperclip then locks on projected months with no files (faded, non-opening "locked" clip), and the `InvoiceFilesModal` swaps its upload UI for a locked notice (`canAttach` prop) so the prime invoice-number chip isn't a bypass; the lock is **year-aware** via `isActualInvoiceMonth(year, monthIdx)` (whole past years actual, future years projected, current year splits at the cutover). Both gate sites (the `tables.jsx` clips + the `App.jsx` `canAttach` prop) read that one flag, so toggling the policy is a single-constant change. Amounts are always editable regardless.
7. **Invoice per-row overrides + writeback + file uploads.** `ytd_actual_override` and `rollforward_override` on `anticipated_invoice` let a user freeze either derived number. NULL = auto-calc; NOT NULL = display verbatim. Clearing the cell writes NULL. **All inline Invoice edits persist to Supabase**: the 12 month columns (`jan_amount`–`dec_amount`) via `updateInvoiceCell`, and `project_name`, `project_number`, `contract_amount`, `type`, `msmm_remaining_to_bill_year_start`, `year` via a whitelist in `updateInvoice` (`INVOICE_COL_MAP` in App.jsx). Writes are optimistic (local state first, then PATCH; no rollback on failure — a toast surfaces the error). PMs flow through `anticipated_invoice_pms` separately. **Per-month PDFs:** prime-side billing PDFs upload to Supabase Storage bucket `invoices` and are tracked in `prime_invoice_files (invoice_id, month, file_path, …)`. Sub-side billing has its own table — `sub_invoices (project_id, company_id, year, month, amount, paid)` for the per-(project, sub-firm, month) amount + the paid flag, and `sub_invoice_files` for the PDFs. Cascade-delete on the metadata rows; the frontend deletes the Storage binary first. **Prime/total per-month paid flags:** the "Project total" row carries its own 12 `{mon}_paid` booleans directly on `anticipated_invoice` (no separate table — the row is already year-scoped), toggled via `updateInvoicePrimePaid` and read back as `primePaid: boolean[12]`. Same three-state cell coloring as subs (attachment → yellow, paid → green, amount-only → red). See migration `20260606120300_prime_invoice_paid.sql`. **Paid cells lock once ticked:** marking paid is open to everyone, but UN-ticking is Admin-only and requires a confirm dialog. For non-admins a paid tick renders with a lock glyph + `not-allowed` cursor and clicking it just surfaces a "locked — only an administrator can unmark" toast; for admins, un-ticking routes through `requestPaidUntick` (App.jsx) → the reusable `ConfirmDialog` (panels.jsx). All three paid surfaces are gated — the prime/total cell, the sub cell, and the `InvoiceFilesModal` paid toggle (so the modal isn't a bypass). DB-level enforcement lives in `20260607140000_lock_paid_invoices.sql` (triggers reject a non-admin true→false on any paid flag); the UI gate keys off `currentUser.role==='Admin'` passed down as `canUntickPaid`. **MSMM-row status mirror:** the Project total row lives at the *bottom* of the expand, but the parent **MSMM row** (the always-visible top row) echoes the total's per-month status as small read-only `.msmm-mirror` badges — a sage check top-left when `r.primePaid[i]`, an accent paperclip top-right when `r.primeFiles[i]` has files (positions echo the total row's paid toggle + clip). Pure indicators (no toggle/open; tooltips only) so you can read paid/attached status at a glance without expanding. Both arrays are loaded upfront on `r`, so the badges show on collapsed rows too. **MSMM values are PURELY DERIVED + read-only for everyone (2026-07):** the MSMM/parent row's dollar figures always compute live (contract: Total CV − Σ sub contracts; month *i*: total[i] − Σ sub months — `msmmContractAuto`/`msmmAtDesc` in tables.jsx) and recalculate on **every** total/sub change through any path — there is **no stored override** anymore. The cells are read-only, there is no create-time MSMM input (`forms.jsx`) or drawer field (`panels.jsx`), MSMM is excluded from ENG↔MHZ sync (`LINKED_INVOICE_SYNC_KEYS`), and the old write plumbing (`updateInvoiceMsmmCell`/`editInvoiceMsmmMonth`/`INVOICE_COL_MAP.msmmAmount`/`msmmOverrideAtDesc`) was removed. Every reader derives it — the table, invoice charts, "Print for Manish" xlsx, and the PDF export — so it can never go stale. Migration `20260708120100_msmm_derived_only.sql` NULLs any lingering overrides; the earlier admin-only guard (`20260608150000`/`20260608160000`) stays as defense-in-depth since the app no longer writes those columns. `onBlockedMsmmEdit` shows an "auto-calculated — edit the Total or a sub" toast on a click. (`msmm_remaining_to_bill_year_start` — the Rollforward starting balance — is a separate admin-editable field, unchanged.)
   **Current MSMM rule (`20260716130000`, superseding the derived-only paragraph above for linked pairs):** on linked ENG↔MHZ and PM↔MHZ PM projects, MSMM is an independently stored, every-user-editable sub on the HZ view. Editing MSMM, another sub, or the project total never rewrites MSMM indirectly. The white HZ first row alone is recalculated as `Project total − Σ(all subs including MSMM)` for every financial column. Unlinked ENG/PM keeps the derived/admin-gated fallback.
8. **Row-level alerts are per-row and wired end-to-end.** Every project row and every Events row supports: tagged recipients, first-fire datetime, recurrence, optional message. Persistence: `confirmAlert` in `App.jsx` inserts three rows (`alerts` + `alert_recipients` + initial pending `alert_fires`). Dispatch: GitHub Actions → `send-alert` → `claim_pending_fires` (atomic) → render email from `subject_table` → Resend (per-recipient idempotency key) → `complete_fire` (flips status + spawns next occurrence for simple recurrences; Edge Function handles custom RRULE via `rrule`). Timezone per-alert (`alerts.timezone`) so weekly/biweekly/monthly math survives DST. Deletes on the parent row trip a BEFORE DELETE trigger that flips `is_active=false` on related alerts — history stays, future fires stop. `alert_fires.status ∈ {pending, processing, sent, failed, skipped}` IS the log table. See §"Alerts dispatch pipeline" below for the full flow.
9. **Smart anchor + offset presets on the bell modal.** `AlertModal` receives `anchors` (populated date fields on the row — `anticipatedResultDate`, `contractExpiry`, etc. from `getRowAnchors(tab, row)` in `data.js`) and shows anchor chips above offset-preset chips (30 min / 1 hr / 1 day / 2 days / Custom). Picking both fills the date + time inputs; inputs remain the source of truth. On submit, `anchor_field` + `anchor_offset_minutes` + `timezone` persist on the alert so the email body can phrase the anchor in plain English ("1 day before the anticipated verdict on Apr 30").
10. **SOQ has been removed in v2.** No `soq` table, no SOQ tab, no Move Forward path. v1 had `beacon.soq` as a parallel-to-Awarded pipeline (with `start_date` and `recurring` fields and its own Quad Sheet gantt strip). The data backfill drops SOQ rows entirely. The Quad Sheet tab itself was also retired (2026-05) — its two surviving panels (the ENG + PM cash-flow charts and the Subs Receivables drill-down) moved verbatim to the top and bottom of the Invoice tab respectively. ## Auth & Roles

- **Login is required.** `App.jsx` boots with `phase="booting"` → reads the Supabase session → `phase="anon"` renders `LoginPage` (calls `signIn` then `fetchCurrentBeaconUser`) → `phase="loading"` runs `loadBeacon()` → `phase="ready"`. `onAuthStateChange` kicks cross-tab sign-outs back to `"anon"`.
- **Two roles, app-enforced + RLS-gated.** `beacon_v2.users.role` ∈ {`Admin`,`User`}. `isAdmin()` in `data.js` keys off the row fetched on login. Writes to `beacon_v2.users` are RLS-gated to Admin via `beacon_v2.is_current_user_admin()` — defense-in-depth so a compromised authenticated user can't flip their own role via direct PostgREST. SELECT stays open to authenticated + anon so PM/attendee pickers work. Other `beacon_v2.*` tables remain permissive-for-authenticated (plus prototype anon CRUD on most) — tighten further as admin-only actions accrue.
- **Admin drawer** lives on the gear icon: tabs = Users / **Alerts** / Appearance. Non-admins see the TweaksPanel (Appearance only) from the same gear. The Alerts tab widens the drawer to ~880px via an `admin-drawer-wide` modifier.
- **Edge Function auth patterns:**
  - `admin-users` — session JWT with `role='Admin'`, validated by re-fetching the users table on each call. (Still pinned to v1 `beacon.users`; works because UUIDs are shared across schemas, but role flips don't propagate to v2 — see the gotcha section.)
  - `send-alert` — dual: service-role bearer (GitHub Actions) **or** an Admin session JWT (the "Run tick now" button). Anon callers get 401/403.
- **Seeding auth users.** `scripts/seed_auth_users.py` mirrors every `beacon.users` row into `auth.users` with password `{first_name}123$` and `app_metadata.role`. Idempotent (PUT on match, POST on miss). Reads from v1 `beacon.users`; the v2 backfill carried IDs forward, so this still produces correct `auth.users` rows for the v2 frontend.
- **Anon write policies are a prototype shortcut.** `20260421120000_allow_anon_write.sql` opens full CRUD to `anon` so creates work before auth was wired. Now that login is live, the `anon insert/update/delete` policies (and the `anon read` policy) should be dropped on any table that should be sign-in-gated — see the security note inside that migration.

## Alerts dispatch pipeline

```
AlertModal  →  confirmAlert (App.jsx)                 ─┐
  • 3 inserts into beacon_v2: alerts + alert_recipients │
    + pending alert_fires (status='pending')            │   (every 60s)
                                                        │        │
                                                        ▼        ▼
                                       beacon_v2.alert_fires  ◀──  GH Actions cron
                                                                │    (alert-tick.yml)
                                                                ▼
                                                 send-alert Edge Function
                                                 1. claim_pending_fires (SKIP LOCKED, marks 'processing')
                                                 2. load alert + recipients + subject row
                                                 3. render email per subject_table
                                                 4. Resend (Idempotency-Key = fire.id:email)
                                                 5. complete_fire ─┬─ status='sent' + spawn next fire (tz-aware)
                                                                   ├─ status='failed' + error_message (retry ≤3)
                                                                   └─ status='skipped' (subject deleted, disabled, etc.)
```

(As of 2026-06 `send-alert` reads `beacon_v2` directly — the arrows above are the live flow once the function is redeployed.)

- **Kill switch:** `ALERTS_ENABLED=false` as an Edge Function secret short-circuits the handler → `{ok:true, disabled:true}`. No redeploy needed.
- **Logs:** `beacon_v2.alert_fires` IS the log table. Studio-friendly query:
  ```sql
  select f.status, f.scheduled_at, f.fired_at, f.error_message,
         a.subject_table, a.subject_row_id, a.recurrence
    from beacon_v2.alert_fires f
    join beacon_v2.alerts a on a.id = f.alert_id
   order by f.scheduled_at desc limit 50;
  ```
  The Dispatch Desk tab renders the same info with vitals + per-alert expand-for-history + retry buttons.
- **Deep links:** `send-alert` builds `{APP_URL}?tab=X&rowId=Y`. `App.jsx` reads query params on BeaconApp mount, sets tab, then a `pendingFocusRowId` effect auto-opens the DetailDrawer when rows include that id; URL cleared via `history.replaceState`.
- **Polymorphic subject resolution:** `alerts.subject_row_id` has no FK (it spans 4 tables in v2: `projects`, `anticipated_invoice`, `events`, `leads`). The Edge Function maps `subject_table` → DB table name and selects by id. A missing row → `skipped` + `is_active=false` on the alert (the BEFORE DELETE trigger also deactivates immediately).
- **Custom RRULE:** `recurrence_rule` is an iCal RRULE string. `complete_fire` returns without spawning for `recurrence='custom'`; the Edge Function parses the rule via `rrule` (npm) and inserts the next pending fire itself.

- **Team Calendar — per-person colour runs at TWO strengths, and which one you get is deliberate.** `identityVars` (team-calendar-shared.jsx) emits a compressed tier (`--u-key` / `--u-ink` / `--u-tint` / `--u-chip`) for the grid, because a week holds a hundred blocks and twenty saturated hues in it is a paint chart; and a vivid tier (`--u-bold`, S 45–85) for the ROSTER surfaces — the people chips (`.bxtc-person`) and the picker rows — where each person appears exactly once and the hue is the key you read the grid by. Three carriers per person there (ring, avatar, name ink) so identity survives losing any one, and the picker's selected tick takes the person's colour rather than the app accent. **`--u-bold`'s lightness is FITTED, not computed** (`fitContrast`): HSL lightness is not perceptual luminance — hsl(60 65% 45%) is more than twice as bright as hsl(240 65% 45%) — so a fixed formula produced rings that measured 2.56:1 on the pastel slot where a non-text UI element needs 3:1. The BLOCK surfaces are fitted the same way and were freed up at the same time: `--u-tint` (the event wash) and `--u-chip` (the initials tile) used to be near-neutral because a crowded slot drew twenty of them; the density cap bounds a slot at ~5 drawn blocks, so they now run at S 58–88 / 52–82 and the grid is genuinely colour-coded per person. Their binding constraint is NOT the hue-coloured type on them — it is `--text-muted`, a fixed grey used by the block's time/location lines, which is the first thing to fail as the wash saturates; the fit walks the wash back towards the surface until that grey clears 4.65:1 (the extra margin absorbs the 0.1-decimal rounding in the emitted `hsl()`). `fitContrast` moves AWAY from the reference colour, derived from which side the start is already on — an absolute light/dark threshold gets the dark-theme wash backwards and quietly makes it less readable. The block's 3px identity rule and `--u-line` also take `--u-bold`. `frontend/tests/identity-contrast.test.mjs` pins every slot in both themes — ring, name, wash, tile, and non-inversion — and reads the real `CALENDAR_PALETTE` out of `data.js` (via `tests/helpers/palette.mjs`) rather than copying it, so adding a slot with a bad hue fails the suite.
- **Team Calendar — the week/day grid caps concurrency and collapses the rest into "+N more" bands.** The grid overlays every selected calendar into ONE day column, and no arrangement of twenty rectangles in a 150px column is readable. The old answer was a cascade that guaranteed each block a 26px BOX and fanned the boxes across the column — but what you see of a block is the STEP to the one on top of it, `step = (colPx - 26) / (cols - 1)`, which shrinks without bound; at twenty blocks in 150px the step is 6.5px, i.e. the 3px identity rule and nothing else, twenty times over. That was the reported "barcode". `frontend/src/calendar-density.js` now puts the floor on the step: `columnCapacity(colPx)` is how many blocks fit legibly, each cluster keeps `capacity - 1` columns and the hidden events are merged into contiguous runs, one synthetic band per run (`resource._overflow`, drawn by `OverflowBlock`, skinned `.bxtc-evt--more` — neutral ramp, dashed hairline, hatched wash, NO owner hue, because it stands for several people). Activating a band opens the existing `DayListDialog` with the events inside it, so nothing is dropped or unreachable. Applied ONLY to week/day in the grid layout: month has rbc's own per-cell "+N more", agenda is a list, and the lane layout gives each person their own row. Ordering inside a cluster tie-breaks on event id — a crowded slot is mostly events with identical start and end, so without it a refetch that reordered ties would silently swap which blocks survive. `capacity === Infinity` (column not yet measured) draws everything, so the first paint never flashes content away. Covered by `frontend/tests/calendar-density.test.mjs`.
- **Team Calendar — the toolbar is OURS, not react-big-calendar's.** rbc renders `components.toolbar` inside `.rbc-calendar`, which on this page sits inside the `.bx-scroll-x` wrapper that lets a seven-column grid keep a readable column width — so the date header, the chevrons and the Today button slid sideways with the grid, and scrolling right to reach a chevron pushed the date off the left edge. `CalToolbar` is now rendered ABOVE that scroller with `toolbar={false}` on `<Calendar>`, and the page's `date` state is the single source of truth: the chevrons move it (`navigateDate`), the header formats it (`rangeLabel`), the fetch window derives from it (`isoWindow`) and rbc receives it as a prop — see `frontend/src/calendar-range.js`, covered by `frontend/tests/calendar-range.test.mjs`. `onNavigate={setDate}` stays wired for rbc's own drill-downs. The header names the RANGE and never the word "Today"; the nav cluster (`‹ Today ›`) sits immediately LEFT of it so a chevron and its result are one glance, and the Today button is the only place the word "Today" appears in the bar — a "Today" badge pinned to the date as well read as one thing that was not changing when the date underneath it was. The button is always rendered, marking itself `aria-current="date"` when the current day is on screen rather than disappearing. Freshness ("Updated 3m ago") lives in the right-hand control group, `hidden` below `xl`, and is on the refresh button's tooltip at every width; the layout switch drops to icons below `lg`. That keeps the bar to ONE row of controls down to ~700px. The fetch window is derived from `effectiveView` (the view actually drawn), not the stored view — phones fall back to Agenda, and deriving it from the stored desktop view fetched a week and rendered a 30-day agenda over it. The people strip (`PeopleBar`) WRAPS with a "+N more" disclosure instead of scrolling sideways, and collapses to a one-line summary via a "Close people panel" button persisted at `beacon.teamCalendar.peoplePanelOpen`. `SelectAllToggle` is the select-all/deselect-all control and appears TWICE with different scopes: in the panel header it is roster-wide, and inside the picker popover it sits directly above the list and acts on whatever the search/department/location filters have left VISIBLE. The picker's copy unions/differences against the existing selection rather than replacing it, so somebody who is selected but filtered out is never silently dropped. Both use the conventional tri-state box (checked / dash / empty) and the conventional semantics: all → click clears, none or some → click selects. The `…` menu keeps the two roster-wide escapes ("Select everyone", "Clear selection") because with a filter on, neither is reachable from the scoped toggle.

## Responsive design

The app runs at phone, tablet, and desktop widths. Entry point: `frontend/index.html`'s viewport is `width=device-width, initial-scale=1, viewport-fit=cover` (formerly pinned to `width=1440`, which forced mobile Safari to render the desktop layout zoomed-out). The responsive layer lives entirely in `frontend/src/styles.css` — no per-component breakpoint JS except the tab-rail auto-scroll.

- **Breakpoint ladder** (mobile-first overrides appended to the end of `styles.css`, ~280 lines): ≤1280 → ≤1024 → ≤840 → ≤640 → ≤440. Plus `@media (hover: none) and (pointer: coarse)` for touch-target sizing, landscape-phone re-centering of modals, `@media print`, and `@media (prefers-reduced-motion: reduce)`. 11 media-query blocks total.
- **Tables keep their grid columns and scroll horizontally** inside `.table-scroll` — we explicitly did NOT collapse to card views (user muscle memory for the grid is load-bearing). Each `.table-scroll` wraps header + rows in a `.table-scroll-body { min-width: min-content }` div so all rows render at a shared width. `min-content` (not `max-content`) is intentional: it resolves to the sum of track minimums (fixed px + `minmax()` first arg), which is exactly what the grid needs to render without clipping — `max-content` would additionally pull in cell-text intrinsic widths and inflate the wrapper past what the grid requires, causing spurious horizontal scroll on wide desktops.
- **Drawer → full-width on phone**; modals (`AlertModal`, `CreateModal`, `MoveForwardPanel`) convert to **bottom-sheets** on portrait phones (slide up from bottom, rounded top corners only) and **re-center** on landscape-phone geometries via `@media (max-height: 500px) and (max-width: 900px)` where a bottom-sheet would cover the whole viewport.
- **Two modal scrim classes exist.** `.overlay` (panels.jsx, forms.jsx, etc.) and `.modal-backdrop` (the six timekeeping modals: `UserDayModal`, `LeaveRequestModal`, `CorrectionModal`, `WeekApprovalModal`, `PunchPromptModal`, `IntervalReclassifyPopover`). Both are now `position:fixed; inset:0` dim scrims (z-58, just under `.modal` z-60) — **`.modal-backdrop` was undefined until 2026-06**, so those six modals never dimmed the page and their outside-tap-to-close silently no-op'd (the wrapper collapsed to 0 height). If you add a timekeeping modal, the `<div className="modal-backdrop" onClick={close}>` wrapper now Just Works.
- **Timekeeping Day editor (`UserDayModal`) mobile.** At ≤640 the modal is full-screen with a pinned header + footer and a single scroll region in between (`.tk-de-scroll` — `display:contents` on desktop so the desktop grid is untouched, `flex:1; overflow-y:auto` on mobile). The right-hand inspector becomes a **slide-up bottom sheet** (`position:fixed`, `.is-active` reveals it, a `.tk-de-insp-scrim` dims + taps-to-dismiss, grabber handle, safe-area padding); the idle inspector's Add button is surfaced as a footer **Add block** button (`.tk-de-foot-add`) since the idle sheet is off-screen on mobile. `EditableDayTimeline` create-by-drag stays mouse/pen-only — touch users add via that footer button and set precise times in the inspector's time inputs; card move + tap-select work on touch (`touch-action:none`), and the selected card's resize handles are enlarged + always-visible on coarse pointers. This fixed the prior bug where the fixed `canvas height:64vh` under the stats/hero pushed the inspector edit form + footer "Done" past `100vh` into the clipped (unreachable) region.
- **Sidebar rail: collapsed by default, hover-expands on desktop (Gmail's pattern).** `railCollapsed` in App.jsx defaults to **true** — the persisted key is read as `!== "0"`, so *unset* means "never chosen", not "expanded". **The key is `beacon.ui.railCollapsed.v2`, and the `.v2` is load-bearing.** v1 was written by a `useEffect` keyed on `[railCollapsed]`, which fires on *mount* and therefore stamped `"0"` (expanded) into storage for every user who had ever opened the app, whether or not they touched the toggle. Honouring those values pinned the rail open company-wide and hid the hover affordance entirely — the collapsed default appeared not to work at all. A fresh key discards that fabricated history, and the write now lives in the toggle's click handler (`toggleRail`), never in an effect: an effect cannot distinguish "the user chose this" from "this is the default". Same trap applies to any future default flip on a persisted UI preference. Everything else is CSS in `beacon.css`, scoped to `@media (min-width: 1024px)`: while collapsed the rail sits at `--sidebar-w-collapsed`, and `:hover` / `:has(:focus-visible)` widens it to `--sidebar-w` with `--shadow-xl`. **The expansion is an overlay, not a layout change** — the shell's grid column stays at the collapsed width, so a 40-column invoice table never reflows out from under the pointer on the way to the nav. Three things are load-bearing: (1) the rail stays an ordinary **in-flow grid item and simply overflows its 60 px track** — an explicit `width` overrides the default `justify-self: stretch`, the item paints from the track's start edge, and grid track sizes are unaffected by an item overflowing them. **Do not reach for `position: fixed` here.** Taking the rail out of flow also removes it from grid auto-placement, which drops `.bx-main` into column 1 — the 60 px one — and crushes the whole page to a sliver; the only way back is pinning `.bx-main` with an explicit `grid-column: 2`, i.e. a second rule that must stay in sync. Overflowing in flow needs no counterpart rule and cannot fail that way. (2) **the inner column never reflows** — `.bx-rail-head/-scroll/-foot` are pinned to the full `--sidebar-w` in *both* states and the rail (`overflow: hidden`) clips them, so expanding changes only the rail's width and the clip rect. An earlier version instead restyled the contents at the collapsed width (icons centred, padding/gap zeroed, labels `display: none`); every one of those jumped discontinuously at t=0 while the width was still tweening, which is what made the animation stutter. Only `width` and `opacity` animate now, and text fades rather than flipping `display` (which cannot tween). Verified by sampling geometry every frame across a hover: `iconX` and `labelX` each hold a single value for all 40 frames. The trade is icons sitting ~2 px left of the strip's centre — scroll padding (8 px) + item padding (12 px) puts a 16 px icon's centre at 28 px, not 30 px; (3) the whole block sits inside the desktop media query, which is what lets the `<1024px` drawer keep its labels without the revert overrides it used to need. Nav buttons carry an explicit `aria-label` because the label span is faded to `opacity: 0` at rest and would otherwise be the only accessible name.
  - **`:has(:focus-visible)`, not `:focus-within`, is the expand trigger.** Clicking a nav item leaves DOM focus on that button, so `:focus-within` held the rail open after the pointer left and the user had to click elsewhere to dismiss it — a real extra click on every navigation. `:focus-visible` matches keyboard focus only, so tabbing still expands the rail while a mouse click does not. Confirmed directly: after a mouse click the rail matches `:focus-within` but *not* `:has(:focus-visible)`, and stays at 60 px. `:has()` adds no browser constraint here — Tailwind v4 already requires Chrome 111 / Safari 16.4 / Firefox 128, all above `:has()` support.
  - **`.bx-navitem::after` is contended.** The collapsed count-dot and the pipeline flow connector (`[data-flow="pipeline"] .bx-navitem + .bx-navitem::after`) both want it, and the dot's selector outranks the connector. The dot is therefore declared **only** inside the resting-state selector — declaring it unconditionally (e.g. to fade it) silently deletes the connector whenever the rail is hover-expanded. The per-item tooltip was dropped — hovering now reveals every real label, so a floating duplicate of the one under the cursor fired at the same moment and only added noise. `z-index: 45` is chosen to sit above the sticky topbar (40) and below the record drawers/modals (50–60) whose scrim must still dim the rail; it applies because `.bx-rail` is already `position: relative`. Width uses `--dur-normal`/`--ease-out` — a strong decelerate that reads as a reveal; `--ease-spring` would overshoot the width and wobble the clip edge, which is the opposite of smooth on a hover. Text fades out faster (`--dur-fast`) than it fades in (`--dur-normal`, delayed 60 ms) so glyphs are never caught half-clipped by the advancing edge. No `prefers-reduced-motion` override is needed — `tokens.css` already collapses the duration tokens to 1 ms under that query.
- **Pipeline tab rail horizontal-scrolls** below 1024 instead of wrapping to multiple rows. `App.jsx` holds a `pipelineRef` and runs a `useEffect` on `tab` that calls `scrollIntoView({ block: "nearest", inline: "center", behavior: "smooth" })` on the active tab — so programmatic tab changes, URL-param deep links, and stale touch-scrolled positions all recover the active tab.
- **Topbar collapses** on phones: `.brand-sub`, the decorative notifications bell, the (currently non-functional) search pill, and the session role chip all hide progressively. The session name hides before the avatar.
- **Stat strip** 4 → 3 → 2 columns; sparkline drops on phones so seven-figure values don't collide with the sparkline SVG.
- **iOS notch respected** via `env(safe-area-inset-*)` on topbar / tabs / page / toast.
- **Admin drawer + Dispatch vitals** reflow: vitals grid 5 → 3 → 2 cols, admin row drops badges onto a second grid row at ≤640 so name/email don't clip at 360 px.

## Progressive Web App (PWA)

The frontend ships as an installable PWA via `vite-plugin-pwa`. Configured in `frontend/vite.config.js`; runtime UI in `frontend/src/pwa.js` (subscribable store + SW registration) and `frontend/src/pwa-ui.jsx` (`PwaInstallChip`, `PwaOfflineChip`, `PwaUpdateToast`). App.jsx mounts the install chip + offline chip in the topbar and the update toast at the page root.

- **The store must hand out SNAPSHOTS, not `state`.** `emit()` in `pwa.js` spreads into a new object before notifying. `usePwa()` pipes what it receives straight into a `useState` setter, and React **bails out of the re-render when the next value is `Object.is`-equal to the current one** — so the original `for (const l of listeners) l(state)` made every notification a silent no-op. Consequence: the "New version available" toast, the install chip and the offline pill could only ever render if their flag was already true at mount, which never happens for an update detected seconds into a session. **The update prompt was therefore invisible in production**, which is the reason non-technical users concluded that clearing the browser cache was the only way to get a new build. If you ever refactor this store, keep the snapshot — a mutable singleton reads as correct and fails silently.
- **Navigations are `NetworkFirst`; `index.html` is NOT precached.** `globPatterns` omits `html` and **`navigateFallback` is explicitly `null`** — vite-plugin-pwa defaults it to `"index.html"`, and leaving it unset injects a `NavigationRoute` bound to the *precache* that is registered **ahead of** `runtimeCaching` and therefore wins every navigation. That cache-first shell was the structural cause of "a normal refresh still shows the old build": the SW answered the reload from the precache, so only a hard reload (which bypasses the SW) picked up a deploy. The shell now comes from the `beacon-app-shell` runtime cache with `networkTimeoutSeconds: 3` and `matchOptions: { ignoreSearch: true }` (so an offline `/?tab=projects` is answered by the single cached `/`). Verify after any workbox change: `dist/sw.js` must contain **no** `new NavigationRoute(` and **no** `{url:"index.html"`.
- **`skipWaiting: true`.** A waiting worker is only released when *every* tab of the app closes — an ordinary reload keeps the old worker in control, so "just refresh" provably could not pick up a deploy. The new worker now activates on install and `clientsClaim` takes over the open tabs; `src/pwa.js` still owns *when* the page reloads, so nobody is yanked mid-edit. Trade-off: the still-running old page is now controlled by the new worker, so a lazy `import()` of a replaced chunk can 404 — handled by the `vite:preloadError` listener in `pwa.js` (one guarded reload, sharing the `beacon.chunkReloaded` sessionStorage flag with App.jsx's export-path handler).
- **Update flow — actively detected, auto-applied, never a required click.** `src/pwa.js` drives detection itself: after the SW is ready it calls `registration.update()` immediately, every 60 s (`SW_UPDATE_POLL_MS`), and on each `focus` / `visibilitychange→visible` / `online` event, plus a `/version.json` heartbeat comparing the live `buildId` against the `__BUILD_ID__` baked into the bundle. Both routes funnel into `raiseUpdate()`: **hidden** tab → apply silently off-screen; **visible** tab → toast with a 45 s countdown (`AUTO_APPLY_MS`) that applies itself, parking at 0 while `userIsTyping()` (focus in an input/textarea/select/contenteditable) so a half-typed cell survives. "Later" snoozes that `buildId` only — the next release prompts again.
- **`applyUpdate()` escalates in tiers, tracked in `sessionStorage.beacon.updateAttempt`.** 1st: activate any waiting worker, else plain reload (enough, because navigations are NetworkFirst). 2nd–3rd: unregister the SW and wipe every cache before reloading — *this is the "clear your cache" step, performed for the user instead of explained to them*. Beyond `MAX_AUTO_ATTEMPTS` it stops reloading and leaves the toast up, because a deploy that never converges would otherwise trap the tab in a reload loop.
- **`PwaUpdateToast` is mounted on both sides of the auth gate** — inside `BeaconApp` when signed in, and next to `LoginPage`/`LoadingScreen` for every pre-auth phase. It used to live only inside `BeaconApp`, so anyone parked on the login screen (the audience most likely to be on a stale build) got no update UI at all.
- **Bootstrap gotcha:** the *currently-installed* SW must first pick up the build containing the above. After deploying it once, fully quit + reopen the installed app (or hard-refresh) so the new worker takes over; every later deploy is then automatic.
- **Manual SW registration** — `injectRegister: false` in vite.config.js; we call `registerSW({ onNeedRefresh, onOfflineReady })` ourselves in `pwa.js` so the same store can also track `beforeinstallprompt` (install chip), `appinstalled` (auto-hide), and `online`/`offline` events (offline pill).
- **Supabase requests are NETWORK-ONLY.** Workbox `runtimeCaching` entries explicitly mark every HTTP verb against `VITE_SUPABASE_URL` as `NetworkOnly` — we never serve cached data from the database; if offline, the request fails and the offline chip surfaces. Google Fonts CSS is `StaleWhileRevalidate`, font files are `CacheFirst` for a year (URLs are content-hashed). (`navigateFallbackDenylist` is gone along with `navigateFallback` — the `request.mode === "navigate"` matcher only ever sees top-level document loads, so `/api/`, `/functions/`, `/auth/` and `/realtime/` can't match it.)
- **Cache budget:** `globPatterns` covers `js/css/ico/png/svg/webmanifest/woff/woff2` — **deliberately no `html`**, see the NetworkFirst bullet above; `maximumFileSizeToCacheInBytes: 5 MB` ceiling per asset; `cleanupOutdatedCaches: true`.
- **`devOptions.enabled: false`** — the SW is **not active in `npm run dev`** (would just slow it down and cache stale dev bundles). To test SW behavior locally, flip to `true` or use `npm run build && npm run preview`.
- **Icons** are checked in under `frontend/public/` and regenerated from the source SVG via `npm run pwa:icons` (`frontend/scripts/generate-pwa-icons.mjs` using `@resvg/resvg-js`). Re-run when the brand mark changes.
- **Vercel cache-control headers** in `frontend/vercel.json` send `Cache-Control: public, max-age=0, must-revalidate` for `/sw.js` and `/workbox-*.js` (so update prompts actually arrive), plus `Service-Worker-Allowed: /` on `/sw.js`. Don't strip those when editing vercel.json.
- **Cloudflare-fronted custom domain caches `sw.js` (the #1 "updates don't appear on my domain" cause).** Production is reachable both straight from Vercel (`beacon-msmm.vercel.app`) and via a Cloudflare-proxied custom domain (`beacon.msmm-ai.com`). Cloudflare caches `.js` at its edge **by default — including the stable-named `sw.js` / `workbox-*.js`** — so on the Cloudflare domain `registration.update()` keeps fetching the *old* worker and the PWA never updates there, even though the Vercel domain updates fine. Vercel already serves those files `max-age=0, must-revalidate`, so the fix is Cloudflare-side: **Caching → Browser Cache TTL → "Respect Existing Headers"** + a **Cache Rule → Bypass cache** for `"/sw.js"`, `"/"`, `"/index.html"`, `"/manifest.webmanifest"`, and paths starting `"/workbox-"` (leave `/assets/*` cached — content-hashed + immutable). Purge Everything once to evict the stale worker. Verify with `curl -sI https://beacon.msmm-ai.com/sw.js` → want `cf-cache-status: BYPASS`/`DYNAMIC` and an `etag` matching the Vercel domain.
  - **Status as of 2026-08-11: still NOT applied.** `https://beacon.msmm-ai.com/sw.js` answers `cache-control: public, max-age=14400, must-revalidate` (4 h — Cloudflare's classic default Browser Cache TTL) even though the origin sends `max-age=0`, and `cf-cache-status` is `REVALIDATED` rather than `BYPASS`. Every other no-cache path (`/`, `/version.json`, `/manifest.webmanifest`) comes back `DYNAMIC` with the origin header intact, which pins the rewrite specifically on Cloudflare caching `.js`. The registration uses `updateViaCache: "imports"`, so the browser still bypasses its HTTP cache for the top-level `sw.js` and updates do get through — but the edge copy is a latent stale-worker risk, and it is the one part of this that **cannot be fixed from the repo**. The NetworkFirst shell + tiered `applyUpdate()` above are the in-app defence that makes a stale worker survivable.

## Working Style
